VISUALUX / HUMAN SETUP GUIDE

Run a complete workflow.

Three local apps with clear and confusing designs. Each example starts at an app entry page and needs two document navigations, multiple interactions, and a visible result.

1. Install and start the playground

From the repository root, use Python 3.11 or newer. Skip environment creation if you already have .venv.

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
playwright install chromium
visualux demo

Alternatively, uv sync --locked installs from the lockfile; run .venv/bin/playwright install chromium and .venv/bin/visualux demo. No frontend build, database, account, or inference service is needed to browse.

Keep this terminal running. Open http://127.0.0.1:8765: the gallery should show three apps and two links per app. Clicking a link starts the corresponding workflow. The server binds only to loopback and makes no model calls on startup.

2. Configure your model

If you installed a wheel without a source checkout, skip the installation commands above. Activate that environment, start from an empty writable directory, and copy the bundled configurations first: cp -R "$VIRTUAL_ENV/share/visualux/examples" ./examples. The demo startup output also prints their installed location.

For agent runs, open a second terminal at the repository root. Copy the examples next to their originals so relative knowledge/output paths keep working. Local configuration copies are ignored by Git.

source .venv/bin/activate
cp examples/lab.toml examples/lab.local.toml
cp examples/reports.toml examples/reports.local.toml
cp examples/device.toml examples/device.local.toml
export LITELLM_PROXY_API_KEY='YOUR_INFERENCE_KEY'

Edit each local file's [model] connection. For an existing LiteLLM gateway:

[model]
name = "litellm_proxy/YOUR_EXISTING_ALIAS"
api_base = "http://127.0.0.1:4000"
api_key_env = "LITELLM_PROXY_API_KEY"
response_mode = "prompted"
# context_tokens = 32768  # replace with the deployment's actual usable limit

The model must accept image inputs and follow the action schema. The alias after litellm_proxy/ is sent unchanged to your gateway. Use an inference key, supplied through the named environment variable. Never put credentials in task descriptions or knowledge files. The examples allow longer time budgets for local inference; these are allowances, not measured latency guarantees.

The planned LiteLLM + Gemma 4 31B trial remains unverified. A preflight checks basic image input before a run; it does not establish UI-reading quality.

3. Run the tasks

visualux run --config examples/lab.local.toml
visualux run --config examples/reports.local.toml
visualux run --config examples/device.local.toml

The lab configuration includes warning investigation and a separate calibration lookup. Device Setup includes successful creation and an explicit invalid-serial recovery task; it grants create permission for this synthetic data. The optional examples/knowledge.md supplies field concepts and test values, without a correct click path.

Keep entry URLs at lab.html, reports.html, or device.html. Start with ?variant=clear; change only that query value to confusing to compare designs using the same tasks, model, and budgets. Each run has its own directory under reports/ with an HTML index, task reports, screenshots, trace, and any downloaded file.

Give the agent a goal, as the example tasks do. These human walkthroughs are not loaded into model requests; keep them out of knowledge/configuration inputs. Confusing designs may produce blocked or uncertain outcomes. Those outcomes and their evidence should remain visible in the report.

4. Check the workflow manually

These checks describe successful paths for humans. App entry pages do not show the answers needed to complete the tasks. Both designs support the same paths and data.

Lab Monitor — choose a lab → explore devices → inspect a device
  1. Open either Lab Monitor variant from the gallery, then choose Lab North. This is navigation one.
  2. The list shows four of eight devices. Use the warning filter or pagination to find the exception. Search also supports the separate Device-03 calibration task.
  3. Open the device detail. This is navigation two. Read the temperature with its unit, warning cause, recommended action, and calibration date.

The confusing variant uses abbreviated status/temperature labels, a low-salience warning, and a tiny detail target.

Report Center — choose a report → filter records → configure and download
  1. Choose North thermal survey from the three-report catalogue. This is navigation one.
  2. Select active records. Confirm the visible subset, then open export configuration. This is navigation two.
  3. Check that the active scope and row count survived navigation. Download CSV and inspect the actual file, not just the UI feedback. The breadcrumb back to the report preserves the selected scope.

The confusing variant uses “A”, vague “Process” controls, and weak completion feedback. Format choices include CSV and JSON; the representative task requests CSV.

Device Setup — inventory → registration form → saved record
  1. Start with the inventory's two existing devices. Open the registration form. This is navigation one.
  2. Enter the requested name, serial, and temperature threshold. For the recovery task, submit the invalid serial first, then correct it. The confusing design clears entered values after a validation error.
  3. Submit valid data. Successful saving opens a separate device record: navigation two. Verify all requested values there.
  4. Refresh the saved record and return to inventory. The record should still exist. Reset demo data and confirm only the original two devices remain.

Browser tests walk all six app/variant combinations and check two real document navigations per workflow, filtering, recovery, file contents, and persisted state. The optional real-model matrix checks completed tasks against private minimum navigation/action counts and expected results. Initial page loading does not count as a task navigation; tab changes and filters do not count as document navigations.

State and reset

All data is synthetic and stored in the browser. Created devices persist across navigation and refresh in the same context. Clear and confusing variants share storage when opened in the same browser profile and origin: use “Reset demo data” before a manual comparison. It explicitly clears created devices and returns to the current app's entry page. Independent agent tasks use fresh contexts by default. No backend cleanup is needed.

Troubleshooting

  • Port already in use: run visualux demo --port 8766 and update each configuration's entry URL to the same port. Use the same hostname consistently; browser storage is origin-specific.
  • Chromium missing or cannot start: run playwright install chromium in the environment and follow Playwright's error guidance for required Linux system libraries.
  • Authentication/model errors: check the named key environment variable, endpoint, and exact deployed alias. The tool does not silently switch providers or response modes.
  • Invalid model response or timeout: confirm image and structured instruction support; use prompted unless your gateway supports JSON/schema mode. Review retained artifacts before adjusting request/task budgets.
  • Missing saved record: check whether you changed browser context, hostname, or port, or reset data. Storage write failures show an error and retain the form values. Corrupt stored data requires an explicit reset.

The apps use ordinary same-tab DOM controls. Canvas clicks, uploads, drag/drop, and multi-tab workflows are outside the agent's current support.
